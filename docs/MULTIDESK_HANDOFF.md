# 멀티 데스크 인수인계

작성 2026-08-25. 다음 세션이 이 문서만 읽고 이어받을 수 있게 쓴다.

## 지금 무엇을 만들고 있나

한 설치 주소 안에 데스크(스페이스)를 여러 개 두는 기능이다. URL 첫 세그먼트로 가른다.

```
https://<주소>/A/files     → A 스페이스
https://<주소>/sea/files   → sea 스페이스
```

관련 이슈: #12 멀티 데스크, #13 닉네임, #10 공개 폴더, #11 사이드바.

## 확정된 요구사항 (사용자 지시)

### 멀티 데스크 (#12)
- 스페이스는 **관리자만** 만들고 관리한다. 멀티데스크 관리 창이 따로 있다
- 일반 유저는 **초대받은 스페이스만** 접속. 초대 없으면 주소를 알아도 거부
- 관리자는 로그인하면 **자기 스페이스 목록**부터 본다. 일반 유저도 여러 곳이면 목록, 한 곳이면 바로 입장
- **나가기 버튼은 갈 곳이 둘 이상일 때만** 보인다. 역할이 아니라 목적지 유무 기준
- 스페이스마다 사용자 명단·역할·용량 제한·채팅·공유 링크·아이콘 배치가 전부 분리된다
- 가입은 기본 데스크에서만(기존 초대 코드). 스페이스 멤버십은 관리자가 가입자를 명단에 추가
- 스페이스 삭제는 등록 해제만 — 파일은 남긴다

### 닉네임 (#13)
- 입장할 때 닉네임을 받고, 접속 인원 표시와 우측 하단 이름이 닉네임으로 보인다
- 관리자 화면에는 구글 이름도 함께, 닉 변경 기록도 보인다
- 자기 이름을 클릭하면 변경
- 허용 문자: 한글·영어·숫자와 `- . ( ) @ ~ # ^ &` — 슬래시 제외

### 공개 폴더 (#10) — 아직 시작 안 함
- 외부인이 로그인 없이 주소로 들어와 받고 올린다
- 화면은 폴더 목록이 아니라 **바탕화면과 똑같이**. 좌측 상단에 `공개폴더: {이름}`
- 나가기 버튼은 데스크 멤버에게만
- **하위 폴더는 아무도 못 만든다**(멤버 포함). 평평하게 유지
- 폴더별 총 용량·파일 크기·개수 상한, 공개 시작·종료 시각
- 접근 권한은 역할 최소선 + 개인 지정 **둘 다**, OR 판정
- 설정 화면에 공개 폴더별 파일 목록·관리 페이지

### 사이드바 (#11) — 아직 시작 안 함
- 우측 여백에 손잡이를 눌러 여는 사이드바
- 추가기능(＋) 버튼 삭제, 상단엔 다운로드 우선만 남김
- 사이드바로 이동: 간이 링크 만들기, 생성된 링크, 다른 데스크에서 받기, 공개 폴더 입장
- 생성된 링크에 권한 — 일반 유저는 자기 것만, 관리자는 전부

### 버전 정책
- 이 묶음은 **0.9.91** 트랙. 0.10.0이 이미 발행돼 뒤로 못 가므로 0.9.9 대신 이 번호
- 0.9.91 < 0.10.0 이라 자동 업데이트에 안 잡히는 것이 **의도된 동작**이다
- 테스트가 끝나면 **1.0.0으로 승격**. 그때부터 기존 데스크들이 업데이트를 받는다
- **사용자 데스크(Youkamii/sharedesk)의 업데이트 워크플로는 실행하지 않는다.** 사용자가 손수 한다

### 핵심 설계 결정

**스페이스 컨테이너는 `.spaces/<slug>`.** 점 접두사라 기존 데스크 목록에 안 뜬다. 기존 단일 데스크는 `folderId: null`로 설치 루트 그 자체를 쓴다 — 그래서 **마이그레이션 스크립트가 없다.** 1.0.0을 받아도 파일이 한 개도 안 움직이고 기존 주소가 그대로 동작한다.

**정체·세션 유효성은 기본 데스크가 단일 진실 원천이다.** 스페이스 명단에서는 멤버십과 역할만 읽는다. 스페이스 명단의 세션 필드로 판정하면 기본에서 철회한 토큰이 스페이스에서 계속 살거나, 새 토큰이 옛 레코드와 어긋나 거부된다. 같은 사람이 스페이스마다 다른 역할을 가질 수 있다.

**주의: `folderId`의 의미가 어댑터마다 다르다.** local은 루트 기준 상대경로, drive는 폴더 id다.

## 남은 작업 — 반드시 이 순서로

### 0. [최우선] 문맥 전달 방식 재설계

**이걸 먼저 하지 않으면 그 위에 쌓는 모든 UI가 흔들린다.**

현재 `space-context.ts`의 `establishSpaceContext`가 `AsyncLocalStorage.enterWith`를 쓴다. `enterWith`는 되돌림 지점이 없어 요청 경계를 보장하지 않는다. Next는 자기 ALS만 `run()`으로 감싸고 이 프로젝트의 `space-store`는 별개 ALS라, 요청 A의 문맥이 다음 요청에 남거나 `await` 뒤에 문맥이 사라질 수 있다.

교차 리뷰에서 두 모델이 정반대로 평가한 지점이고, Next 소스를 확인한 결과 위험 쪽이 맞다.

**해야 할 일**: `enterWith`를 버리고 요청 핸들러 전체를 `runWithSpace(...)`로 감싸는 래퍼를 만든다. `requireSession`이 문맥과 세션을 함께 돌려주는 형태로 바꾸고, 보호 라우트 38개가 그 안에서 돌게 한다. 공개 라우트 6개(`api/auth/*`, `api/share/[linkId]`, `api/invitations/code`, `api/update-policy`)는 명시적으로 기본 문맥으로 감싼다.

### 1. 클라이언트 배선

`src/app/files/`와 `src/lib/client/` 어디에도 스페이스 헤더를 붙이는 코드가 **없다**. 주소창이 `/sea/files`여도 API 호출에는 헤더가 없어 기본 데스크를 읽고 쓴다. 지금 멀티 데스크가 반쪽인 이유다.

`fetch` 호출을 한 곳으로 모으고 거기서 헤더를 넣는 게 낫다. FilesView가 9600줄이라 호출부가 흩어져 있다.

### 2. proxy matcher 정리

matcher 밖 라우트(`/api/chat`, `/api/presence`, `/api/share`, `/api/me/nickname` 등)는 클라이언트가 보낸 헤더를 그대로 받는다. 라우트마다 같은 헤더가 "신뢰되는 값" 또는 "무시되는 값"으로 갈려 상태가 섞일 수 있다. matcher를 넓히거나, 0번 래퍼가 모든 라우트에서 문맥을 명시적으로 정하게 한다.

### 3. UI

- `/spaces` 페이지: 목록 + 관리자용 생성·관리
- 로그인 리다이렉트: 갈 곳 둘 이상이면 목록부터
- 나가기 버튼 (목적지 둘 이상일 때만)
- 닉네임 UI: 입장 폼, 표시 교체, 관리자 기록 화면

### 4. 나중에 다룰 것

- **스페이스 공유 링크**: 소비 라우트 `/api/share/[linkId]`가 항상 기본 데스크를 본다. 링크에 스페이스가 인코딩돼 있지 않아 구조적으로 스페이스 링크를 못 연다. desk2desk(#7)도 같은 영향을 받는다
- **삭제 후 슬러그 재생성**: 등록만 지우고 폴더·명단이 남아, 같은 슬러그를 다시 만들면 옛 멤버가 approved 그대로 접근을 되찾고 옛 파일이 붙는다
- **cron·인증 콜백**: 문맥 없이 돌아 기본 데스크만 본다. 스페이스의 만료 링크는 영원히 청소되지 않는다
- **닉네임 저장 위치**: 정체는 기본 데스크가 진실 원천인데 `setUserNickname`이 스페이스 문맥에서 돌면 스페이스 명단에 쓴다. 기본 문맥으로 고정해야 한다
- **drive 루트 생성 경합**: eventual consistency 상황에서 두 요청이 서로의 폴더를 canonical로 골라 각자 삭제할 수 있다
- **등록부 무결성**: 서로 다른 슬러그가 같은 `folderId`를 갖는 상태를 막지 않는다

## 작업 방식 (지켜야 할 것)

- 비자명한 구현은 kickoff 절차: 태스크 분해 → 이슈 → 기능별 실행 검증 → 커밋(#이슈) → 푸시 전 적대 리뷰
- **실행한 것만 완료다.** 코드를 읽고 "될 것 같다"로 판정하지 않는다
- 커밋 메시지는 다음 세션이 커밋만 읽고 무엇을·왜 했는지 알 수 있게
- `Co-Authored-By` 트레일러 절대 금지
- 검증 명령: `npm test`, `npx tsc --noEmit`, `npx eslint src/ tests/`, `npm run build`
- 파이프를 거치는 검증은 종료 코드를 따로 확인한다(`| tail`을 쓰면 tail의 코드가 나온다)
- 소스에 리터럴 제어문자를 넣지 않는다. 정규식에 필요하면 유니코드 이스케이프 표기로 쓴다
