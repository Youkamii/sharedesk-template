# ShareDesk का निर्माण AI को सौंपना

यदि Google Cloud या Vercel अनजाना लगता हो, तो निर्माण का काम किसी कोडिंग AI को सौंपा जा सकता है। यह दस्तावेज़ इस तरह बनाया गया है कि AI रिपॉज़िटरी और टर्मिनल की जाँच करे, और केवल उन्हीं स्क्रीन के लिए एक-एक चरण करके मार्गदर्शन करे जहाँ उपयोगकर्ता को स्वयं क्लिक करना है।

यह गाइड **उस होस्ट के लिए है जो अपने Google Drive संग्रहण को कई लोगों के साथ, हर किसी के अपने Google खाते से साझा करने वाला नया ShareDesk खोल रहा है।** पहले से बने ShareDesk में आमंत्रित प्रतिभागी इंस्टॉल नहीं करते।

## उपयोग कैसे करें

1. रिपॉज़िटरी और टर्मिनल संभाल सकने वाले किसी कोडिंग AI में अपनी ShareDesk रिपॉज़िटरी खोलें।
2. नीचे दिया अनुरोध हूबहू भेजें।
3. Google Cloud और Vercel की स्क्रीन पर जब कोई ऐसा काम आए जो उपयोगकर्ता को स्वयं करना है, तो AI द्वारा बताए गए केवल उसी एक चरण को पूरा करके `पूरा हुआ` उत्तर दें।
4. Client secret, refresh token, callback URL जैसे गुप्त मान चैट में न चिपकाएँ। AI द्वारा बताई गई लोकल फ़ाइल या सेवा की स्क्रीन में उपयोगकर्ता स्वयं दर्ज करता है।

## हूबहू कॉपी करने के लिए अनुरोध

```text
इस रिपॉज़िटरी में ShareDesk का प्रोडक्शन वातावरण बनाओ।

लक्ष्य ऐसा ShareDesk बनाना है जिसमें एक होस्ट के Google Drive संग्रहण को कई लोग अपने-अपने Google खाते से साथ मिलकर उपयोग करें। आमंत्रित व्यक्ति को GitHub, Vercel या Google OAuth सेट किए बिना, प्रोडक्शन पते पर साइन इन करके केवल आमंत्रण कोड दर्ज करना पर्याप्त होना चाहिए।

कार्य के सिद्धांत:
1. सबसे पहले इस रिपॉज़िटरी की docs/AI_INSTALL.hi.md और docs/INSTALL.hi.md शुरू से अंत तक पढ़ो, और docs/INSTALL.hi.md को इंस्टॉल प्रक्रिया का मानक मानो।
2. काम से पहले वर्तमान स्थिति की पुष्टि करो। वर्तमान रिपॉज़िटरी, ब्रांच, git status, origin, जुड़ी हुई GitHub रिपॉज़िटरी और Vercel प्रोजेक्ट, स्थिर Production पता, .env.local की आवश्यक प्रविष्टियाँ भरी हैं या नहीं, तथा मौजूदा OAuth व Drive कनेक्शन के निशान — यह सब मान उजागर किए बिना जाँचो।
3. जो चरण पहले पूरे हो चुके हैं, उन्हें मत दोहराओ। मौजूदा रिपॉज़िटरी और Vercel प्रोजेक्ट दोबारा मत बनाओ, और मौजूदा OAuth क्लाइंट, Audience स्थिति, refresh token तथा Drive ID को अनुमान के आधार पर मत बदलो या रद्द करो।
4. यदि उपयोगकर्ता को Google Cloud या Vercel की स्क्रीन पर स्वयं कुछ करना पड़े, तो एक बार में केवल एक चरण समझाकर रुक जाओ। उपयोगकर्ता के "पूरा हुआ" कहने पर परिणाम की पुष्टि करके अगले एक चरण पर बढ़ो।
5. Client secret, SESSION_SECRET, refresh token, callback URL, आमंत्रण कोड जैसे गुप्त मान चैट, इशू, कमिट या स्क्रीनशॉट में न माँगो और न ही प्रिंट करो। उपयोगकर्ता को यह बताओ कि वह उन्हें .env.local, लोकल टर्मिनल इनपुट, Google Cloud और Vercel की स्क्रीन में स्वयं डाले। callback URL केवल उसी लोकल टर्मिनल में उपयोगकर्ता से चिपकवाओ जहाँ npm run setup -- --finish पूछता है।
6. रिपॉज़िटरी की फ़ाइलें बदलनी पड़ें तो हर अलग सुविधा या सुधार के लिए पहले GitHub इशू बनाओ, और सत्यापन के बाद केवल उन्हीं फ़ाइलों को अलग कमिट करके इशू संख्या दर्ज करो। .env.local और गुप्त मान कभी कमिट मत करो। ट्रैक की गई फ़ाइलों में कोई बदलाव न हो तो खाली इशू या खाली कमिट मत बनाओ।
7. यह अनुरोध वर्तमान में चल रही मेरी ShareDesk रिपॉज़िटरी में आवश्यक बदलाव, सुविधावार GitHub इशू व लोकल कमिट, वर्तमान कार्य-ब्रांच का push, और जुड़े हुए मेरे Vercel प्रोजेक्ट के Production डिप्लॉय की अनुमति देता है। काम से पहले वास्तविक लक्ष्य रिपॉज़िटरी, ब्रांच, Vercel प्रोजेक्ट और Production पते की पुष्टि करो, तथा मूल टेम्पलेट या किसी और की रिपॉज़िटरी व प्रोजेक्ट को मत छुओ।
8. स्वचालित जाँच पास होने और वास्तविक प्रोडक्शन पुष्टि में अंतर करो। जिसकी पुष्टि नहीं की, उसे पूरा हुआ मत बताओ। रिपॉज़िटरी बदली हो तो जाँच और सुविधावार कमिट पूरे करने के बाद ही push व डिप्लॉय करो।

कार्य का क्रम:
1. वर्तमान स्थिति को एक तालिका में रखो, और उसे पूरा / अधूरा / पुष्टि आवश्यक में बाँटो।
2. मेरी GitHub रिपॉज़िटरी और Vercel प्रोजेक्ट न होने पर ही उन्हें बनाओ या जोड़ो, और न बदलने वाला Production पता नोट करो।
3. Google Cloud में एक ही प्रोजेक्ट के Drive API, Branding, Audience, Data Access और Web application OAuth क्लाइंट की जाँच करो। docs/INSTALL.hi.md के तीन redirect URI और चार scope ठीक-ठीक मिलते हैं या नहीं, यह उपयोगकर्ता से जँचवाओ।
4. रिपॉज़िटरी में npm ci चलाओ और .env.local सुरक्षित रूप से तैयार करो। Google Client ID और Client secret उपयोगकर्ता से फ़ाइल में स्वयं डलवाओ।
5. npm run setup चलाकर होस्ट की Google सहमति शुरू करो। सहमति के बाद callback URL उपयोगकर्ता से npm run setup -- --finish के प्रश्न में स्वयं चिपकवाओ, और AI उस मान को न पढ़े और न दोबारा प्रिंट करे।
6. setup द्वारा बनाए गए ADMIN_EMAILS, SESSION_SECRET, STORAGE_DRIVER=drive, GOOGLE_REFRESH_TOKEN, DRIVE_ROOT_FOLDER_ID, DRIVE_STATE_FOLDER_ID मौजूद हैं या नहीं — केवल यही, मान उजागर किए बिना जाँचो।
7. npm run dev से लोकल में होस्ट साइन-इन, फ़ोल्डर बनाना, रीफ़्रेश के बाद बने रहना, ट्रैश से बहाल करना और /admin तक पहुँच जाँचो।
8. npm test, npm run lint, npx tsc --noEmit --incremental false, npm run build चलाओ और परिणाम दर्ज करो। बदलाव हों तो सुविधावार कमिट पूरे करने के बाद केवल अनुमत वर्तमान ब्रांच को push करो।
9. आवश्यक मान Vercel के Production एनवायरनमेंट वेरिएबल में ले जाओ और Production दोबारा डिप्लॉय करो। PUBLIC_BASE_URL को स्थिर Production origin के अनुसार सेट करो, और LOCAL_STORAGE_ROOT तथा SHAREDESK_SHARE_TEST_EMAIL प्रोडक्शन एनवायरनमेंट में मत डालो।
10. प्रोडक्शन पते पर होस्ट साइन-इन, फ़ाइल सहेजना, रीफ़्रेश, ट्रैश से बहाली, /admin और आमंत्रण कोड बनाना — यह सब वास्तव में जाँचो।
11. किसी एक अलग Google खाते को आमंत्रित करके उससे अपने खाते से साइन इन करवाओ और कोड दर्ज करवाओ। होस्ट और प्रतिभागी दोनों खातों से वही फ़ाइल दिखती और डाउनलोड होती है — यह स्वयं जाँचो। इस पुष्टि से पहले साझा उपयोग का सत्यापन पूरा मत कहो।
12. सभी मुख्य सुविधाएँ काम करने लगें, तभी docs/INSTALL.hi.md का Vercel Firewall नियम जोड़ो और 429 व्यवहार जाँचो।

पूर्णता की रिपोर्ट नीचे दिए प्रारूप में दो।

स्थिति: पूरा / आंशिक रूप से पूरा / अटका हुआ
प्रोडक्शन पता: <पुष्टि किया गया स्थिर Production पता>

पुष्टि हो चुका:

- Google OAuth callback और Drive कनेक्शन:
- लोकल साइन-इन, फ़ाइल सहेजना, ट्रैश, व्यवस्थापक स्क्रीन:
- प्रोडक्शन साइन-इन, फ़ाइल सहेजना, ट्रैश, व्यवस्थापक स्क्रीन:
- दो Google खातों से एक ही फ़ाइल देखना व डाउनलोड करना:
```

ऊपर दिए अनुरोध में **वर्तमान कार्य-ब्रांच का push और मेरे Vercel Production डिप्लॉय तक सौंपने वाला वाक्य** शामिल है। यदि डिप्लॉय तक नहीं सौंपना है, तो भेजने से पहले कार्य सिद्धांत क्रमांक 7 को इस तरह बदल दें।

## वे क्षण जब AI को अवश्य रुकना चाहिए

नीचे दिए मान और स्क्रीन उपयोगकर्ता को स्वयं संभालने होते हैं। AI केवल एक चरण बताकर प्रतीक्षा करता है।

| क्षण | उपयोगकर्ता को स्वयं क्या करना है | AI क्या परिणाम जाँचे |
|---|---|---|
| Google Cloud OAuth सेटअप | Drive API, Audience, scope और redirect URI स्क्रीन पर जाँचकर सहेजना | सेटिंग की प्रविष्टियाँ और पते [प्रोडक्शन इंस्टॉल गाइड](./INSTALL.hi.md) से मेल खाते हैं या नहीं |
| Client ID और secret डालना | लोकल `.env.local` में स्वयं दर्ज करना | मान प्रिंट किए बिना केवल यह जाँचना कि दोनों प्रविष्टियाँ खाली नहीं हैं |
| होस्ट की Google सहमति | ब्राउज़र में होस्ट खाता चुनकर सहमति देना | setup अगले चरण तक बढ़ता है या नहीं |
| callback URL डालना | `npm run setup -- --finish` जिस लोकल टर्मिनल में पूछे, वहीं स्वयं चिपकाना | केवल setup की सफलता जाँचना |
| Vercel में गुप्त मान डालना | Vercel के Production एनवायरनमेंट वेरिएबल स्क्रीन में स्वयं दर्ज करना | आवश्यक वेरिएबल के नाम और डिप्लॉय में उनका लागू होना |
| प्रतिभागी खाते की जाँच | अलग Google खाते से साइन इन करके आमंत्रण कोड दर्ज करना | दोनों खातों से एक ही फ़ाइल दिखती और डाउनलोड होती है या नहीं |

## इंस्टॉल पूरा कहने की कसौटी

केवल कोड जाँच और डिप्लॉय सफल होने से काम पूरा नहीं होता। निम्न की भी वास्तव में पुष्टि करनी होगी।

- स्थिर Production पते पर होस्ट का Google साइन-इन काम करता है।
- फ़ोल्डर और फ़ाइलें रीफ़्रेश के बाद भी बनी रहती हैं, और ट्रैश में डाले गए आइटम बहाल किए जा सकते हैं।
- `/admin` में आमंत्रण कोड बनाया जा सकता है।
- कोई अलग Google खाता आमंत्रण कोड से भीतर आ जाता है।
- होस्ट और प्रतिभागी दोनों खातों से एक ही फ़ाइल दिखती और डाउनलोड होती है।
- रिपॉज़िटरी में बदलाव हुए हों तो सुविधावार इशू और कमिट आपस में मेल खाते हैं, और push व डिप्लॉय केवल अनुमति मिलने पर ही हुए हैं।

इंस्टॉल की स्क्रीन और त्रुटियों का विस्तृत विवरण [ShareDesk प्रोडक्शन इंस्टॉल गाइड](./INSTALL.hi.md) में देखें।

यदि पहले से चल रहे इंस्टॉल को नए संस्करण में बदलना है, तो उसे नए सिरे से न बनाएँ — [ShareDesk अपडेट गाइड](./UPDATE.hi.md) का AI अनुरोध उपयोग करें।
